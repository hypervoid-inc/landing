## From one good run to a reusable procedure

AI workflow automation is useful when a procedure contains research, judgment, writing, or tool use that cannot be reduced to a fixed data mapping. Construct combines durable workflow steps with an agent that handles those less predictable parts.

A workflow can include agent work, connected-app actions, and in-app notifications. Published versions are preserved so a future edit does not silently change a run that already started. Run history makes the procedure easier to inspect and improve over time.

The sequence that works is to do the job once conversationally, confirm the output is right, and only then encode it. A workflow written before the job has ever succeeded is a guess about the steps. A workflow written afterwards is a record of steps already known to produce the result you wanted.

## A worked example: the Monday competitor digest

Consider a recurring task: every Monday, check five competitors' pricing pages, note anything that changed since last week, and save a dated summary for the team.

**Run it once.** Ask Construct to gather the current pricing for each competitor and summarize it. It uses web search and fetch for public pages, and a live browser run for any page that needs interaction. You review the output and correct the framing.

**Encode it.** Save the procedure as a workflow: an agent step that gathers and compares pricing and saves a dated summary to Files, and a notification step so you see the run even when nobody is watching the workspace.

**Schedule it.** Add it to Construct's Calendar as a recurring Monday job. The scheduler runs it server-side and reconciles missed or delayed work rather than depending on an open browser tab.

**Inspect it.** Each run leaves step results, retry information, and Activity summaries. Agent steps link back to their chat sessions, so a week where the summary looked wrong can be opened and read rather than guessed at.

The durable output is a versioned procedure, a dated summary each week, and a run history that makes the procedure improvable. When a competitor redesigns a pricing page and the step starts returning less useful results, the run history is where that shows up.

## Run now or put it on the Calendar

Construct's Calendar is a scheduler for agent work and workflows. Create a one-time job, define a recurring schedule, run it immediately, or cancel it from the same workspace. Scheduled runs happen server-side, so they do not depend on an open browser tab or your laptop being on.

This makes recurring operating work practical: weekly market research, an inbox summary, a customer follow-up list, or a report assembled from several connected systems. Google Calendar can be connected as an external app, but Construct's native Calendar controls when agent jobs run.

Workflow runs start on demand or from the Calendar. For a workflow that should react to incoming mail, schedule an inbox check at the interval you choose; the agent reads what arrived since the last run and handles it.

## Use the right execution surface

Each step can use the surface that fits the job. Structured app actions are best for reliable updates. Web search and fetch handle public research. A live browser covers interactive sites, including logins completed during that run. The sandbox terminal processes files, runs scripts, and generates artifacts, with files saved under the workspace persisting after the run.

Live browser runs and shell state exist for the duration of the run, so anything a later step or a later week depends on should be written to workspace files while the run is in progress. ## Inspect every run

Workflow automation should be debuggable. Construct keeps run state, step results, retry information, and Activity summaries. You can open resulting files and review connected-app actions; agent steps also link to their chat sessions, and the agent can ask for missing information during interactive work.

Construct's workflows do not pause for approval yet, so for a workflow that posts publicly, emails customers, or updates shared records, have it save drafts for a person to send, and run it manually a few times before it goes on a schedule. Reviewing the first several runs is the cheapest way to catch a step that behaves differently than intended.

## Before you start: designing for linear runs

Construct workflows run as a straight sequence of steps, which keeps them readable: a sequence you can walk, not a graph you have to debug. A few patterns follow.

- **Conditional work** belongs inside an agent step. The agent reads the situation and decides what to do; the workflow itself does not fork.
- **Multi-stage procedures** can be split into separate workflows scheduled at different times, with workspace files carrying state between them.
- **Approval-gated work** works best as an on-demand workflow that a person starts after reviewing, or as a scheduled run that saves drafts.
- **Jobs that run once** are quicker to assign in chat than to encode, and a procedure still changing weekly is worth running in chat until its shape settles.

## When might a trigger-action tool still fit?

- Purely deterministic, high-volume mappings with no judgment step.
- Work that must react within seconds of an event.
- A flow that needs built-in branching, delays, or fan-out today.

For a procedure that is stable, repeated, and needs enough judgment that a fixed mapping would be brittle, Construct is the better fit.
