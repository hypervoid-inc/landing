Construct connects your own tool server by URL: paste its HTTPS address into Apps, and the agent can discover and call up to 200 of its tools alongside the live integration catalog. Wiring the same thing up yourself means hosting an agent, building tool discovery, validating arguments, and re-checking access on every scheduled run before your first lookup works.

For founders and small teams, Construct is the simplest place to put an internal tool in front of an AI employee. It validates every call against your tool's own schema, lets you decide which agents may use the server, saves the results to workspace files your team can open, and runs the job on the Calendar while your laptop is closed. This guide walks through how it works, one tool built end to end, and the permission boundaries around it.

## Why do this in Construct?

- **Add a server in one step, with no vendor review.** Paste the endpoint into Apps with Add MCP. Your server stays private to your workspace.
- **Every call is checked before it is sent.** Construct fetches the current tool list and validates the arguments against that tool's input schema, then sends the call.
- **You choose which agents can use it.** Each agent's settings list the installed apps it may use. Turn your server off for every agent that does not need it.
- **Results land in files, not a chat thread.** The agent writes its table or report to workspace files, and a run that stops at step 30 keeps steps 1 to 29.
- **It runs on a schedule, and access is re-checked each time.** Put the job on the Calendar and it runs server-side. Every run re-checks the install, the agent's access, and the tool's schema.
- **Your tool sits next to the apps you already use.** The same agent can call your server and connected apps such as Gmail, Notion, Linear, or HubSpot in one task.

## What is custom MCP, and when do you need it?

The Model Context Protocol (MCP) is an open standard for exposing tools to AI applications. A server lists its tools, each with a name, a description, and a JSON schema for its inputs, and an AI application calls them over JSON-RPC.

Construct already connects to supported business apps through its live integration catalog, including Gmail, Google Calendar, Notion, Linear, Jira, GitHub, HubSpot, and Airtable. Custom MCP covers the rest:

- the system is yours, such as an internal service or database, and no catalog will ever list it;
- the catalog app exists but lacks the one action you need;
- you want the agent to use a narrow, reviewed interface rather than a whole account.

The third reason is the underrated one. A tool that can only "look up approval status" is easier to reason about than a connected account that can read, send, and delete.

## How does custom MCP work in Construct?

1. **Add the server.** In Apps, choose Add MCP and enter the endpoint URL, the MCP path (`/mcp` by default), and optionally an app ID. Adding apps is an owner or admin permission in a team workspace by default.
2. **Construct reads the tool list.** It asks the server for its tools and keeps up to 200 of them. Tool names, descriptions, input schemas, and annotations such as `readOnlyHint` come from your server.
3. **The agent discovers tools by need.** When a task needs something, the agent searches across installed apps and your server's tools by what they do, then loads the schema of the one it picked.
4. **Each call is checked, then sent.** Construct fetches the current tool list, validates the arguments against that tool's input schema, and sends the call. The text in the result goes back to the agent.

The current requirements, so you can build to them:

<ArticleTable caption="Custom MCP requirements in Construct">

| Requirement | Current behavior |
| --- | --- |
| Address | Public HTTPS URL; private and local network addresses are refused |
| Transport | JSON-RPC requests over HTTPS POST, answered with JSON |
| Methods used | Listing tools and calling tools |
| Time per call | 15 seconds |
| Response size | Up to 512 KB |
| Redirects | Up to two, and only to the same origin |
| Tools read | Up to 200 per server |
| Result | Text content is passed to the agent; structured content is passed as JSON when there is no text |
| Authentication | Construct sends a short-lived, Construct-signed bearer token with each call; there is no field yet for your own API key or custom headers |

</ArticleTable>

## Before you start

A few things to set up deliberately so the first run works:

- **Build for a known caller.** Construct sends a short-lived, Construct-signed bearer token with each call, and there is no field yet for your own API key or custom headers. Make the server narrow, read-only where possible, rate limited, and without bulk export tools. If the data is sensitive, keep it behind a server you can protect.
- **Put the server on the public internet.** Construct refuses private and local network addresses, so a server on your laptop or office network needs a public HTTPS endpoint first.
- **Expose tools.** Construct uses MCP tools. Resources, prompts, and requests from the server back to the user are not used, so wrap anything you need as a tool.
- **Keep each call under 15 seconds.** For long jobs, return a job ID quickly and offer a second tool that checks status.
- **Ask for drafts before writes.** Construct does not ask before every tool call, so tell the agent which tools not to call until you say so, as the approvals prompt below does.

Custom MCP is one of several ways Construct reaches your systems. If the app is already in the catalog with the action you need, connect it instead. If the system has a web interface but no API, the [live browser](/blog/ai-agent-browser-and-terminal/) can read it. If people need a screen rather than the agent, have Construct build a private [workspace app](/blog/build-internal-tools-with-construct/), which declares exactly which apps and HTTPS origins it may reach. For a one-off data pull, import the file into Files and let the agent work on it in the terminal ([where agent work goes](/blog/ai-agent-files-and-artifacts/)).

## A concrete job: an approvals lookup for client reports

This example is illustrative, not a customer case. A small agency tracks client sign-off for reports in an internal service. Every Friday, someone checks which reports are approved before sending them.

**Build the smallest server.** Two tools are enough: one that reads, one that writes. Mark the reading tool as read-only so every system that respects MCP annotations knows the difference.

```json
{
  "tools": [
    {
      "name": "get_approval_status",
      "description": "Return the approval status and approver for a client report ID.",
      "inputSchema": {
        "type": "object",
        "properties": { "report_id": { "type": "string" } },
        "required": ["report_id"]
      },
      "annotations": { "readOnlyHint": true }
    },
    {
      "name": "mark_report_sent",
      "description": "Record that an approved report was sent to the client.",
      "inputSchema": {
        "type": "object",
        "properties": { "report_id": { "type": "string" } },
        "required": ["report_id"]
      }
    }
  ]
}
```

**Add it and limit who can use it.** Add the server in Apps. Then, in each agent's settings, turn it off for every agent that does not need it. In this agency only the reporting agent keeps it.

**Give the job.**

> For each report dated this week in the reports folder of every client in Team/clients, call get_approval_status. List approved and unapproved reports in a table and save it to Team/approvals/2027-01-22.md. Do not call mark_report_sent; I will tell you which ones to mark after I send them.

**Check the result.** The table is in Files, and Activity shows one line per lookup, linked to the chat ([what Activity records](/blog/ai-agent-activity-log/)). When the account manager has sent the reports, a second message asks the agent to mark them.

**Schedule it once it is boring.** Put the lookup on the Calendar for Friday mornings. Every scheduled run re-checks that the server is still installed, that the agent is still allowed to use it, and that the tool's schema still matches, so removing access takes effect on the next run, not after someone edits the schedule.

We have not yet run this server against Construct and measured it.

## What are the permission boundaries?

The MCP specification is blunt about the stakes: "Tools represent arbitrary code execution and must be treated with appropriate caution" ([MCP specification, 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18)). The same section says hosts must obtain explicit user consent before invoking any tool. Construct does not ask before every tool call; the consent you give is choosing which servers are installed and which agents may use them. Here are the boundaries that exist today.

- **Workspace install.** A server is installed for a workspace. In a team workspace, installing apps is an owner and admin permission by default, and an owner can grant or remove it.
- **Per-agent access.** Each agent's settings list the installed apps it may use. Turning one off removes it from that agent's tool search and calls.
- **Shared chats use shared tools only.** In a team group chat, the agent works with workspace-approved apps and team files, never one member's private files or personal connections.
- **Guests get no tools.** If you open a Slack or Discord install to everyone, people who are not on its allow list get a read-only agent with web search and memory lookup, and no apps.
- **Scheduled runs re-check access.** Calendar items and workflows store which tool to call, never credentials, and each run re-checks the install, the agent's access, and the current schema.
- **Calls are not retried automatically.** Calls to connected apps and MCP tools run once, so a failed write is not quietly repeated.
- **Results are treated as data.** Text coming back from MCP tools, like web pages and email, reaches the agent marked as external data whose instructions should not be followed. That reduces, but does not remove, the risk of a hostile result steering the agent. Our [prompt injection explainer](/blog/ai-agent-prompt-injection/) goes deeper.

The biggest boundary is the one you design into the server. A tool that cannot delete cannot be talked into deleting.

## What to check in any agent's custom tool support

If you are comparing products, ask each one these questions. Construct's answers are in bold.

1. Can you add a server by URL without a vendor review? **Yes.**
2. Can you restrict a server to specific agents? **Yes, per agent.**
3. Who in a team can install one? **Owners and admins by default.**
4. Are arguments validated before the call? **Yes, against the tool's own schema.**
5. What are the time and size limits per call? **15 seconds and 512 KB.**
6. How does the product authenticate to your server? **A Construct-signed token with each call; custom credentials are not supported yet.**
7. Does it respect read-only annotations? **Yes, when a chat is saved as a workflow.**
8. Do scheduled jobs re-check access each run? **Yes, every run.**
