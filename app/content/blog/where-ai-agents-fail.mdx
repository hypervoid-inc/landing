## Why we looked at real runs instead of benchmarks

Benchmarks tell you how capable a model is on a fixed set of tasks. They do not tell you how a scheduled Monday report fails on the fourth Monday, or which tool a business agent was holding when it stopped. That is the question buyers ask us, and it is one we can answer from our own aggregate records without reading anyone's work.

Published research has mapped part of this already. Toby Ord found that agent success across task lengths fits "a constant rate of failing during each minute a human would take to do the task," which "implies an exponentially declining success rate with the length of the task" ([Ord, arXiv:2505.05115](https://arxiv.org/abs/2505.05115)). A Berkeley-led team built a taxonomy of how multi-agent systems fail, with "14 unique modes, clustered into 3 categories," from over 1,600 annotated traces across seven frameworks ([Cemri et al., arXiv:2503.13657](https://arxiv.org/abs/2503.13657)). Both studies use research tasks and research frameworks. This report asks the same questions of ordinary business runs: research, reports, inbox work, and app updates that small teams hand to an agent.

We build Construct, so weigh this accordingly. The data comes from one product, its users, and its tools. We publish the method in full below so you can judge how far the results travel, and we are publishing them whether or not they flatter the product.

### What counts as a run

A **run** is everything an agent does in response to one request, from the moment the request arrives until the agent stops. A request can be a chat message, a message in Slack, Telegram, or a Discord slash command, an email to the agent's own inbox, a scheduled job firing from the Calendar, a step in a workflow, or a subtask delegated to a temporary agent. Each of those starts its own run.

If a run is automatically carried forward after reaching its step budget, the continuation counts as part of the same run, not as a new one. {/* TODO: confirm with engineering how continued segments are linked in the records, and whether to stitch them before counting. State the final rule here in one sentence. */}

### What counts as a step

A **step** is one cycle in which the model decides what to do next and, usually, calls one or more tools: open a page in the browser, run a terminal command, read a file, call a connected app, send an email. It is the same unit Construct's plans meter as "steps per task": up to 50 on Lite, 150 on Starter, and 1,000 on Pro ([pricing](/pricing/)). A step that calls several tools at once is still one step; we attribute it to the tool category of its first tool call. {/* TODO: confirm the attribution rule against how multi-tool steps are recorded; if the records allow it, report multi-tool steps separately. */}

### What counts as a failure

Every run ends with one outcome label. We group them like this:

<ArticleTable caption="How each run outcome is counted">

| Outcome | What it means | Counted as |
| --- | --- | --- |
| Completed | The agent finished and gave a final answer | Finished |
| Reached the step budget | The run used every step its plan allows without finishing | Failure |
| Errored | The run stopped on an error it could not recover from | Failure |
| Stopped without an answer | The run ended without a final answer and was not continued | Failure |
| Waiting on a person | The agent stopped to ask a question or needed a permission | Handed back, not a failure |
| Interrupted | A person stopped the run | Excluded from failure rates |
| Deferred | The run was postponed to continue later | Excluded until it resolves |

</ArticleTable>

Two choices here matter. First, "completed" means the agent said it was done. It does not mean the output was right. Checking correctness would require reading the work, which we will not do, so this report measures where runs stop, not whether finished runs were good. Our piece on [why agent work is cheap to make and expensive to check](/blog/agent-verification-gap/) covers that second problem. Second, a run that stops to ask a question is doing its job. We report those separately because a high rate of them on scheduled runs, where nobody is there to answer, is a finding in itself.

### Where a run failed

For each failed run we record:

- **Failure step:** the step number of the last step that ran.
- **Failure position:** the failure step as a share of the plan's step budget, so a Lite run failing at step 40 and a Pro run failing at step 800 are both "late".
- **Failure tool:** the tool category of the last step that called a tool.

The last tool before a failure is evidence, not proof, of the cause. A browser step can be where a run stops because an earlier file step wrote the wrong input. We say "failed on" rather than "failed because of" throughout.

### Recovery after a failure

A failed run is **recovered** if the same agent starts another run on the same job within 24 hours and that run completes. "The same job" means the same conversation, the same scheduled job, or the same workflow. We report the recovery rate and the **retry ratio**: the retry's step count divided by the failed run's step count. A ratio well under 1 suggests the retry started from saved work instead of starting over. It is a proxy, not a direct measure of steps saved, and we label it that way in every chart. {/* TODO: data. Also report recovery at 1 hour and 7 days as a sensitivity check. */}

### Query plan

The analysis runs in five passes, all on aggregate tables:

1. **Select runs.** All runs that started inside the period, minus the exclusions above. Output: one row per run with start source, plan tier, step count, outcome label, and start time rounded to the hour.
2. **Categorise steps.** Join each run's step records to the tool-category mapping. Output: one row per step with run hash, step number, and tool category.
3. **Locate failures.** For every failed run, take the last step, its number, its position in the budget, and the last tool category used.
4. **Link retries.** For every failed run, find the next run on the same job by the same agent within 24 hours, and record its outcome and step count.
5. **Aggregate and suppress.** Build every table below from those three outputs, then suppress small cells and drop all hashes before export.

## What each finding would mean if you are buying an agent

We wrote this section before seeing the numbers, so it covers the outcomes we think are plausible. When the data is in, we keep the paragraphs that apply and delete the rest. {/* TODO: data. Keep only the scenarios the data supports; delete the others rather than hedging. */}

**If most failures happen in the first few steps,** the problem is setup, not stamina. Early failures usually mean a missing connection, a permission the agent does not have, or an instruction it could not act on. For a buyer, the test is the first supervised run: watch it, fix what it trips on, and the long-task maths matters less than you feared.

**If the failure rate per step is flat,** length is the enemy, exactly as the p^n model says. A job twice as long fails far more than twice as often. The fix is structural: cut the job at its natural seams, make each piece leave a file behind, and let the next run skip finished work. That is the argument of [your agent has a half-life](/blog/agent-task-half-life/), and a flat curve here would be real-world support for it.

**If the failure rate rises late in long runs,** something accumulates: context grows, earlier mistakes compound, or the agent loses track of the goal. Shorter runs help even more in that case, and so does writing intermediate state to files instead of relying on what is still in the conversation.

**If browser steps fail most per thousand steps,** prefer a structured connection whenever the app has one, and keep the browser for sites with no integration. Pages change, load slowly, and hide content behind clicks; an app action through the integration catalog does not.

**If connected-app steps fail most,** the usual causes are expired connections, missing permissions, and rate limits. Check connection health before scheduling a job, and give the agent the narrowest access that still lets it finish.

**If terminal steps fail most,** look at long-running commands. Sandbox commands share a five-minute runtime cap on every plan ([terms](/terms/)), so a long data job should be split into shorter commands that write results to files as they go.

**If many runs end at the step budget,** the plan limit is binding for real work, not just in theory. Split the job or choose a plan with a bigger budget. We will report this honestly even though it is a commercial finding about our own plans.

**If scheduled runs stop to ask questions far more than chat runs,** the instructions are missing inputs that a person would normally supply in conversation. Put every input the job needs into the instructions or a workspace file before you schedule it.

**If most failed runs are finished by the next run with a low retry ratio,** resumable design works in practice: saved progress turns a failure into a delay. **If retries mostly start over,** saved progress is not being used, and the instruction pattern in the half-life post (describe the work that remains, not the whole job) matters more than any product feature.

## How this connects to the agent half-life

Our earlier piece, [your agent has a half-life](/blog/agent-task-half-life/), worked from arithmetic: a 95% reliable agent finishes a 48-step job about 8.5% of the time, because 0.95 to the 48th power is about 0.085. That post had no data of its own. This one is the check. The model is not a fringe idea: METR, which tracks how long a task frontier agents can finish with 50% reliability, reports that this length "has been doubling approximately every 7 months for the last 6 years" ([METR](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/)). Longer horizons raise p; they do not change the shape of p^n.

Three things make the comparison less direct than it sounds, and we account for each.

- **Steps are not minutes.** Ord measures task length in the minutes a human would need. We measure it in agent steps. A constant rate per step and a constant rate per human-minute are only the same model if steps take roughly equal human time, which they do not. We test the per-step version because it is the one a buyer can act on.
- **The step budget cuts runs off.** A Lite run cannot go past 50 steps. Counting those stops as failures would make long runs look worse than they are, so the survival curve treats them as censored and the outcome tables count them separately.
- **People choose which jobs to give an agent.** If users only hand long jobs to agents they already trust, long runs will look more reliable than they would be on a random job. We cannot correct for that, so we name it.

If the observed curve tracks p^n, the practical advice from the half-life post stands with real data behind it. ## Limitations

- **One product.** Construct's users, plans, tools, and models shape every number. Another agent product with different tools would fail in different places.
- **No measure of quality.** A completed run may still be wrong. This report cannot see that.
- **Model mix changes.** Model updates during the period and Pro accounts using their own model keys mean the "agent" here is not one fixed model. {/* TODO: data. Report the share of runs billed to customers' own keys, and rerun the headline numbers without them as a sensitivity check. */}
- **Last tool is not root cause.** The tool a run stopped on is where to start looking, not a diagnosis.
- **Retries are inferred.** We link a retry to a failure by job and timing. A person may have changed the instructions in between, which would make a retry look more efficient than resumption alone explains.

## What this means if you are choosing an agent

Whatever the tables show, four questions decide whether a failed run costs you a few minutes or the whole job. Ask them of any agent you are considering. This is how Construct answers them.

- **Does finished work survive a stopped run?** Construct saves reports, spreadsheets, and scripts to workspace files as it produces them. A run that stops at step 30 still leaves steps 1 to 29 behind, so the next run can start from what is already there instead of starting over.
- **Is the step budget big enough for your job?** Construct meters steps per task: up to 50 on Lite, 150 on Starter, and 1,000 on Pro ([pricing](/pricing/)). Count your job's steps against that before you schedule it, and split anything longer into pieces that each leave a file.
- **Does it keep working when nobody is watching?** Calendar schedules run on Construct's servers with your laptop closed: 3 scheduled tasks on Lite, 10 on Starter, and 50 on Pro. A scheduled run reports back in the web app with a notification.
- **Can you correct what it relied on?** If a run went wrong because the agent used an outdated fact, open its memory, correct or forget the fact, and every later run uses the fix.
- **Can you find where it stopped?** Activity records each action with a short reason, which is usually enough to see the step a run stopped on. It covers a limited window, so have important jobs append a line to a run log file as well.

One thing to set up deliberately: Construct's workflows run their steps in order and do not pause for approval yet, so for anything customer-facing, ask for drafts and send them yourself once you have checked them.

Then test it on your own work. Pick the job you most want to hand to an agent and count its steps. Run it on demand a few times, note the step where it stops, and compare that with the tables above. If it fails early, fix the setup. If it fails late, cut it into pieces that save their work. Then put it on the Calendar.
