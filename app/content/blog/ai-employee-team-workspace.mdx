A shared AI workspace lets several people use the same agents, files and connected apps while each person's own chats stay private. In Construct this is a team workspace: the owner's paid plan covers everyone in it, with no seat charge and no member limit, and three roles (owner, admin, member) decide who can connect apps, create agents and invite people. Team files, workspace memory and group chats are shared; one-to-one chats and private files are not.

This guide covers the people side: how teammates join, what they can see of each other's work, and which plan limits they draw on together. How to split the work between several agents is a separate question, answered in [how to structure an AI agent team](/blog/ai-agent-team-structure/).

## Who pays, and which limits the team shares

Creating a team workspace needs a paid Construct plan or a new account's unused free allowance, and the owner's plan pays for all the agent work done inside it. Members do not need a subscription of their own. Model usage, bring-your-own-key settings (Pro only) and plan limits all resolve to the owner.

Two limits are pooled across every workspace the owner owns, personal workspace included, no matter which member created the item:

- **Agents.** Lite allows 2, Starter 5 and Pro 15, counting the built-in Construct agent in each workspace. A new team workspace starts with its own Construct agent, so on Lite, creating one can use your second agent slot.
- **Scheduled tasks.** Lite allows 3 active schedules, Starter 10 and Pro 50, counted across all of the owner's workspaces. If a member tries to add one past the limit, the schedule is refused. Paused schedules do not count, so pausing one frees its slot.

Usage is one allowance for the whole team, so one person running long research jobs draws it down for everyone. Settings, Usage shows where it went. Yearly billing brings the plans to $7.50, $39 and $199 a month ([pricing](/pricing/)).

## Roles and what each one can do

Every member has a role, and the role sets their default permissions. Most labels below are the switches in the **Manage access for** dialog in Settings, People; listening, memory, settings and billing are not switches there.

<ArticleTable caption="Default permissions by role in a Construct team workspace (v2 source, checked 2026-10-26)">

| Permission                                    | Owner | Admin | Member |
| --------------------------------------------- | ----- | ----- | ------ |
| View workspace files                          | Yes   | Yes   | Yes    |
| Add, edit and delete files                    | Yes   | Yes   | Yes    |
| Chat with agents                              | Yes   | Yes   | Yes    |
| Use installed apps                            | Yes   | Yes   | Yes    |
| Install and remove apps                       | Yes   | Yes   | No     |
| Install and remove skills                     | Yes   | Yes   | No     |
| Create and manage agents                      | Yes   | Yes   | No     |
| Manage group chats                            | Yes   | Yes   | Never  |
| Turn on listening in Slack, Discord, Telegram | Yes   | Yes   | Never  |
| Govern workspace memory                       | Yes   | Yes   | Never  |
| Invite people                                 | Yes   | Yes   | No     |
| Manage regular members                        | Yes   | Yes   | No     |
| Workspace settings                            | Yes   | Yes   | Never  |
| Billing, delete workspace, transfer ownership | Yes   | Never | Never  |

</ArticleTable>

"No" means off by default. An owner or admin can switch it on for one person under **Fine-tune access**: a member who maintains your app connections can get **Install and remove apps**, and a contractor can lose **Add, edit and delete files** and keep read access. "Never" is enforced in code, not in the dialog: group chats, listening and memory governance decide what the agent reads and keeps from people outside the workspace, so they stay with owners and admins. Turning off **View workspace files** also turns off editing.

Admins have one more limit: only the owner can invite, promote or manage an admin.

## How people join

There are two ways in, both from Settings, People.

1. **Email invitation.** Under **Invite people**, type the address, pick the **Role** and press **Send invite** (or **Invite as admin**, which only the owner sees). The person gets an email with a join link that works for 14 days, and only for that address: someone signed in with a different email is refused.
2. **Invite link.** Under **Invite links**, choose **Expires after** (1 day, 7 days or 30 days; 7 is the default) and **Uses** (No limit, 1, 5, 10, 25 or 100 uses; No limit is the default), then press **Create link**. Owners can also choose the role. A workspace can have 25 active links, and **Revoke link** stops one at once.

For a link you post in a team channel, set a use count that matches the headcount. Anyone who has the link can join until it expires or runs out.

## What teammates can see of each other's work

This is the part to understand before you invite anyone.

**Chats.** Each person's one-to-one chats with an agent are theirs. A teammate using the same agent sees their own conversations, not yours. The agents themselves are shared: anyone with **Chat with agents** can talk to any agent in the workspace.

**Files.** Files has a Team area everyone with file access can open, and a private area per person that nobody else can browse. You can share a single private file with the whole team or with named people.

**Group chats.** A group has a lead agent that answers when nobody is mentioned, optional specialist agents that answer when mentioned, and a visibility setting: **Members only** or **Everyone in workspace**. New members can read the full history. An admin can see that a members-only group exists but must join it to read it, and joining posts "joined the group and can now view its full history" in the group, so nobody is read silently.

**Memory.** There is personal memory and workspace memory. Workspace memory is shared, but memories tied to one agent or one chat stay with the member whose conversation produced them.

**The sandbox.** Each person's one-to-one chats run in their own sandbox in the workspace, the only one that mounts their private files. Group chats run in a separate workspace sandbox that never mounts anyone's private files, and in a group the agent works only from team files, workspace memory, files posted to the group and the workspace's apps.

**Activity.** Each person sees Activity for the work they started. There is no combined admin feed, so work the whole team should be able to review belongs in a group chat ([what Activity records](/blog/ai-agent-activity-log/)).

## Connected apps act as whoever connected them

Apps in a team workspace belong to the workspace. Owners and admins connect them from Settings, Connections, and every member with **Use installed apps** can then use them through their agents. The account behind the connection does not change: when a member's agent sends from a connected Gmail, it sends as the person who connected it, because the call names the installer's connected account.

So connect team accounts (the shared support inbox, the company CRM user) rather than your own. If one agent should not touch an app, open that agent's settings and turn the app off under **App access**; the switch is per agent and applies to everyone who uses that agent. Our post on [what your AI agent can delete](/blog/what-can-your-ai-agent-delete/) covers how far a connection reaches.

Slack works the same way. Only an owner or admin can add Construct to Slack, and a mention in a channel runs on the installer's account. Teammates who want their own agent in Slack link their Slack identity with a code from the Messaging page in Settings, sent to the bot as `/link <code>`. The [Slack briefing guide](/blog/ai-agent-slack-briefing/) covers the access settings.

## When someone leaves, or the owner changes

Removing a member ends their access at once: they lose the workspace, every members-only group they were in, and their sandbox is destroyed. Their private files stay in the workspace, unseen by anyone, and return if the same person is invited back.

A member can leave on their own. The owner cannot leave without first transferring ownership, and transfer works only to someone who already has paid access, because plan limits and billing move with the owner.

Deleting a team workspace is permanent and owner-only. You type the workspace name to confirm, and its files, agents, chats, memory and installed apps are removed. Export what you need first. A personal workspace cannot be deleted on its own; it goes with your account.

## Setting up a team workspace

1. **Create it.** From the workspace switcher, choose **Create workspace** and name it.
2. **Invite an admin first** if someone else will run day-to-day setup.
3. **Connect shared accounts** in Settings, Connections, using team logins.
4. **Create the agents** you need and set **App access** on each, so an agent only sees the apps its job needs.
5. **Make one group chat per shared job**, with the agent that does that job as lead.
6. **Move the job's files to Team** and run it once in the group, where everyone sees the result. Our guide to [where agent work goes](/blog/ai-agent-files-and-artifacts/) shows how files and outputs are kept.
7. **Put recurring work on the Calendar** and check the pooled schedule count before you hand out permissions to create more.
8. **Invite everyone else** with a link capped at your headcount.

## Things Construct does not do for teams

There is no SAML single sign-on and no SCIM provisioning; people sign in with Google, an emailed link or a password. There is no per-member usage cap and no combined activity feed for admins. If your company requires any of these, that decides it before anything else in this post does.
