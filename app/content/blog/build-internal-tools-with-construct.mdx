## What counts as an internal tool

An internal tool is software your own team uses to run the company: a dashboard of launch numbers, a queue of refund requests, a tracker for renewals at risk, an intake form for design requests. Small teams usually keep these in a spreadsheet or wait for an engineer, because a real app means hosting, sign-in, connecting to the data and someone to fix it when an API changes. That is why the dashboard in the film spent 41 days in a backlog even though it was a few queries and a page of charts.

Construct takes those jobs off the list. The agent writes the app, Construct hosts it inside your workspace, your connected apps supply the data, and the same agent keeps the app working when you ask for changes. Nobody on the team has to read the code, though it stays in your Files if someone wants to.

## How to build an internal tool with AI in Construct

1. **Ask for the tool.** Say who will use it, what they need to see or do, and where the data lives. If the app holding the data is not connected yet, Construct asks you to connect it.
2. **The agent looks at the data first.** It runs a few small queries against the source, writes a short brief as the build's checklist, and asks you a question only when two readings of the request would lead to different apps.
3. **It writes and checks the app.** The agent writes React and TypeScript into `Apps/<app-id>/` in your Files and draws the app an icon. Construct compiles every file on its own servers, checks that imports stay inside the app, and runs a design review that catches problems such as content cut off at the edge or a page that scrolls twice.
4. **You follow the build in one card.** The chat shows a single card with one line of progress. It ends on Ready with an Open app button, or on Couldn't build with a Fix button that sends the error straight back to the agent.
5. **The app opens beside the chat that built it.** On a computer it appears next to the conversation; on a phone you tap Open. To change something, say so in the same chat, or point at the part of the app you mean and the agent gets that element in its next message.

## Live data from PostHog, Google Analytics and the rest of your stack

An app reads from your connected apps through queries it declares when it is built. A query can only use read-only tools, such as PostHog's query and trend tools, Google Analytics reports or a Gmail search, and Construct rejects one that would change anything. Its settings are typed, like a choice of date ranges, so nobody using the app can rewrite the query underneath. An app can declare up to 12.

Results are cached for between 5 and 60 minutes (15 by default) and shared by everyone who opens the app, and an open app fetches again when that window runs out. The Refresh button forces a new read, at most every 30 seconds. Construct draws the status itself: a Live badge when every source refreshed on time, with "Updated 2 min ago" on hover, a warning that names the source when one fails, such as "Can't reach PostHog", and no badge at all when an app has no live data to show.

A dashboard is only worth sending to a board if its numbers match the source. Before it finishes a dashboard, the agent compares the headline numbers with the integration's own overview. When we ran Construct's PostHog overview recipe against our own project on October 26, 2026, visitors, pageviews, sessions and bounce rate came out within a few events of PostHog's web analytics.

Apps also keep records of their own, such as the items in a refunds queue, saved as JSON in your workspace. When the agent or a teammate changes a record, every window that has the app open updates without a reload.

One gap to plan around: Construct does not read X or LinkedIn post analytics, so the film's table of impressions per post is not something it can fill today. If your launch links carry UTM tags, the same table can come from PostHog or Google Analytics, with visits and signups per post.

## Share it with your team, or with a link

Every app starts private. Its creator, or a workspace owner or admin, can open it up in two steps:

<ArticleTable caption="Who can open a Construct app at each sharing level">

| Level | Who can open it | What they can do | Sign-in |
| --- | --- | --- | --- |
| Private | You | Everything | Yes |
| Workspace | Every member of your workspace | Use it, add data and run its actions; a change in a connected app asks them first | Yes |
| Public link | Anyone with the link | View only | No |

</ArticleTable>

Teammates run the creator's latest working build and share one set of app data, so a refund marked done by one person is done for everyone. Editing the app itself stays with the person who built it. A personal workspace offers Private and Public only.

Paste a public link into Slack and it unfurls as a card with the app's icon, name and description and a chip for each live source. Construct draws that card rather than screenshotting the app, so your numbers never end up in a chat's image cache. The link opens on any phone or laptop without an account.

Public links are built to be safe to forward:

- Visitors can only view. The app runs the queries it declared, on the creator's behalf, and nothing typed into the page can be sent anywhere.
- Before you turn a link on, the share panel names the data it will serve and flags fields that identify people, such as email addresses, so the agent can drop them first.
- Search engines and AI crawlers are blocked from the page, while link previews in chat apps still work.
- Turning Public off revokes the link at once, Reset link swaps it for a new one, and workspace owners can switch public links off for everyone.
- A link that spreads costs one call to each source per refresh window, however many people open it.

## When the AI gets something wrong

Mistakes are cheap to undo. A change that fails to build never replaces the working app, so your team keeps using the last good version while the agent repairs the new one. Construct keeps the last 10 builds of every app. Undo on the build card or Versions in the app's menu puts an older one back, source and live app together, and leaves the app's data alone. If two builds in a row fail, the card offers Restore instead of another Fix.

The agent works from evidence. Every app reports its console, network and runtime errors to Construct, with credentials stripped, and keeps them for seven days. The agent reads them before it changes anything, a crashed app shows an "Ask agent to fix" button, and you can open the same logs in an inspector beside the app. Whoever built an app can download its full source as a zip at any time.

## What a Construct app can do, and where it stops

<ArticleTable caption="What a Construct workspace app supports">

| Capability | Support |
| --- | --- |
| Interface | React and TypeScript, up to 32 files |
| Charts | Line, bar, sparkline, ranked bar lists and stat tiles, with colours checked for colour blindness and a table for screen readers |
| Live data | Read-only queries to connected apps, up to 12 per app |
| Saved data | JSON records in your workspace that update live for everyone using the app |
| Actions in connected apps | Only the apps it declares; in a shared app, teammates approve before it writes for them |
| AI inside the app | Summarise, draft or extract, and label or score up to 100 items at a time, billed to the workspace owner and turned off on public links |
| Web requests | Only to the exact HTTPS addresses the app declares |
| Packages | React and Construct's own libraries; npm packages are not installed |
| Hosting | Inside your workspace, with nothing to deploy |

</ArticleTable>

Every app declares what it needs, and Construct denies anything else at runtime. A tracker that only keeps its own records gets no access to your connected apps. An app can also draft a message to the agent about itself, but you are the one who sends it, so an app never starts agent work or spends usage on its own.

The limits are worth knowing before you start. Saved data is key-value JSON, so an app that needs real database queries across thousands of rows is a poor fit for now. Live data refreshes while someone has the app open rather than on a schedule, so the first person to open it after a quiet night sees the last cached numbers until the refresh lands. And a Construct app is for your team: a customer-facing product belongs on its own hosting.

| Coding agents such as Claude Code or Cursor | AI writes the code, your engineers host and maintain it | Whatever your engineers wire up | Your own deployment | Depends on each vendor's plan |
| Construct | Construct's agent builds and maintains it inside your workspace | Read-only queries to connected apps, marked Live | Private, workspace, or a public read-only link | $9 a month, with no per-seat fee |

Construct fits a small team without a spare engineer that wants a tool on data it already has in PostHog, Google Analytics or another connected app, shared with the team in Slack the same day. Another option is the better pick in some cases. Use Retool when engineers are building tools on your own production database for a large internal user base. Use Lovable or a coding agent when the app is a product your customers will use. A spreadsheet is still fine when one person tracks a few rows.

## Which plan to start on

Apps come with every plan, and team workspaces have no per-seat fee, since usage comes from the owner's plan. A tool with several data sources is a long task, though, and plans cap the steps the agent can take per task: Lite ($9 a month) allows 50, Starter ($59) allows 150 and Pro ($299) allows 1,000. A simple tracker fits on Lite. For a dashboard across two or three sources, the 7-day Pro trial gives the first build room to check its numbers and finish.
